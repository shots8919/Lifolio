# Lifolio 2.0 再設計 ── Phase3: 変更禁止領域の抽出

> 既存業務ロジック・データの保護を最優先とするための区分。
> 区分は **変更禁止 / 要注意（条件付き変更可） / リファクタ可能** の3段階。

---

## 🔴 変更禁止（ロジック・データの意味を保持すること）

| 対象 | 理由 | 補足 |
|---|---|---|
| 振込額計算アルゴリズム（`CalculatePage.calculate` の手取り→比率→按分→端数処理） | 過去の確定値と整合する公平按分の中核。端数の非対称処理は意図的仕様 | UIは作り直してよいが**計算式は1:1で移植**すること |
| `account_records` のスキーマ・カラム意味・単位 | 確定済み月次データの保存形式。本番に実データあり（想定） | カラム削除/型変更/意味変更は禁止。追加は可（後方互換） |
| `DeductItem{label, amount}` の構造と `*_deduct_items` jsonb | 控除内訳の保存契約 | |
| 月一意制約 (`account_records.month`) と upsert(delete+insert) の意味 | 月次スナップショットの同一性 | |
| `account_settings` の控除設定スキーマ（`user_settings` jsonb 形状） | 設定の永続化契約 | |

---

## 🟡 要注意（移行・改修の影響が波及。理由を説明の上で慎重に変更）

| 対象 | リスク | 移行時の注意 |
|---|---|---|
| `authStore` の persist（`localStorage: lifolio_auth`） | Supabase Auth へ移行すると認証ゲートの実体が変わる | 既存ログイン状態の扱い・ログアウト導線を要設計 |
| RLS ポリシー（全許可 `using(true)`） | **要修正だが**、安易に絞ると現行クライアント（anon全アクセス前提）が即時に全機能停止 | 認証移行とRLS厳格化は**同一マイグレーションで一体実施**が必要 |
| `app_settings.auth_hash` / `gemini_api_key`（平文・anon可読） | 認証/AIキーの保管方式を変えると既存導線が壊れる | キーはサーバ側（Agent Server）へ退避が前提 |
| `plansApi.deleteOld()`（1ヶ月超を物理削除） | 履歴を残したい将来要件と衝突。データ損失リスク | 削除→論理アーカイブ化を検討 |
| `ai_proposals`(最新1件) / `meal_shopping_lists`(最新5件) の物理削除保持 | 「AI履歴を保存する」将来要件と真っ向から衝突 | 履歴テーブル設計の見直しが必要 |
| `"shota"/"miyu"` ハードコード | 多人数・汎用化・Supabase Auth の user_id 化と衝突 | 全層に散在。識別子戦略の決定が前提 |

## 🟢 リファクタ可能（積極的に再設計してよい）

| 対象 | 方針 |
|---|---|
| 全UI（Tailwind直書き・インラインstyle・トースト等） | Flutter移行 or React再設計で刷新可。計算式とデータ契約のみ保持 |
| 認証層（クライアント側SHA-256比較） | Supabase Auth へ全面置換 |
| AI層（`gemini.ts`=Groq直叩き、脆いJSONパース、キーのクライアント露出） | Agent Server + Claude Agent SDK へ移設。命名も是正 |
| account系のデータアクセス（Page内 supabase直呼び） | API/Repository層へ抽出（mealApi同様の整理） |
| ナビゲーション/ルーティング/レイアウト | 再設計可 |
| `extractJson` の手動サニタイズ | 構造化出力（JSON mode / tool use）で代替 |

---

## 移行の鉄則（本番データ保護）
1. **本番DBへの直接変更は禁止**。まず本番スキーマ/データのダンプ取得（バックアップ）。
2. 認証移行とRLS厳格化は**セットで**行い、移行前に開発環境で全機能の回帰確認。
3. `account_records` への変更は「追加のみ・後方互換」。破壊的変更が必要な場合は必ず理由提示＋承認。
4. 物理削除系（`deleteOld`・最新N件保持）は、履歴保存要件確定まで**挙動を温存**（勝手に消さない）。

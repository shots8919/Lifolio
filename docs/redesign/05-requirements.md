# Lifolio 2.0 ── Phase5: 要件定義書（ドラフト v0.1）

> 対象: 夫婦向けAIライフマネジメントプラットフォーム。
> 前提は Phase4 の確定回答（`redesign-decisions` / `04-risks-and-architecture.md §5`）に従う。
> 本書は要件の合意形成用ドラフト。未決事項は「❓未決」で明示。

---

## 0. コンセプトと原則

- **コンセプト**: 夫婦2人の生活（家計・食事・買い物・タスク）をAIが横断支援する基盤。
- **AI権限の鉄則**: AIは自律的にDBを更新しない。常に **提案 → ユーザー承認 → 実行**。
- **既存資産の保護**: 家計の振込計算ロジックと `account_records` は意味を保持（変更禁止／追加のみ）。
- **本番保護**: 本番DBへの直接変更禁止。変更は開発環境で回帰確認 → 承認 → 反映。

---

## 1. 対象ユーザー / 認証 / データ分離

| 項目 | 要件 |
|---|---|
| ユーザー | 本人 + 妻 の2名（将来拡張余地は残す） |
| 認証 | **Supabase Auth** へ移行（現クライアント側ハッシュ比較を廃止） |
| アカウント方式 | **各自アカウント ＋ 同一「世帯(household)」に所属** |
| データ分離 | `household_id` 単位でRLS。操作者は `user_id` で識別 |
| 既存識別子 | `"shota"/"miyu"` ハードコードを `household_members`（user参照）へ移行 |

**移行方針（認証）**
1. `households` / `household_members`（user_id, role, display_name, color等）を新設。
2. 既存の単一データを 1世帯に紐付け（バックフィル）。`account_records` 等に `household_id` を追加（NOT NULL化は移行後）。
3. RLS厳格化は**認証移行と同一マイグレーションで一体実施**（中途半端だと現行機能が停止するため）。
4. anon全アクセスポリシーは、Agent Server経由アクセスへ切替後に撤去。

❓未決: 既存の `auth_hash` ログインから Supabase Auth への移行時、初回はパスワード再設定（招待メール）でよいか。

## 2. 家計管理（既存維持 ＋ AI分析追加）

### 2.1 維持（変更禁止）
- 振込額計算ロジック（手取り→比率→按分、端数はmiyu側吸収）。`02-business-logic-spec.md §B` の数式を1:1で保持。
- `account_records` スキーマ・`account_settings` の控除設定。
- UIは刷新可。計算式・データ契約のみ不変。

### 2.2 AI数値分析（新規・読取専用）
- **対象データ**: `account_records` のみ（給料・控除・振込額・目標残高・現在残高・到達状況）。
- **提供する分析**: 給料推移 / 控除推移 / 振込額推移 / 目標到達状況 / 月次・前月比・前年同月比。
- **制約**: 数字の提示・要約のみ。**推測・自動修正・DB書込は禁止**（読取専用）。
- ⚠ **食費推移・支出推移は対象外**: account_records に食費/支出の金額が無いため算出不可。将来「支出簿」機能を追加するまで保留（別要件）。

❓未決: 食費分析を将来やる場合の元データ（支出簿 / 買い物リストに価格付与 / レシート読取）はどれを想定するか。

## 3. レシピ機能（全面再設計）

| 入力手段 | 要件 |
|---|---|
| URL | **Agent Serverがページをfetch → 解析**（現状のLLM文字渡しを廃止）。og/構造化データ(recipe schema.org)優先抽出 |
| YouTube | サーバ側で動画メタデータ・字幕/概要欄を取得して解析 |
| 手入力 | 既存フォーム踏襲（再設計可） |
| AI生成 | 条件からAI生成（提案→承認で保存） |

| 保存 | 要件 |
|---|---|
| お気に入り | フラグ管理（既存 `is_favorite` 踏襲） |
| 独自レシピ | 世帯のレシピとして保存 |

- 解析は「提案（抽出結果プレビュー）→ ユーザー確認・編集 → 保存」。
- コンプライアンス: 取得元の規約・robots.txt遵守、低頻度・キャッシュ前提。

❓未決: YouTube字幕取得の手段（公式Data API / 字幕エンドポイント）と、取得不可時のフォールバック挙動。

## 4. 献立機能

- **主用途**: 1週間献立。**副用途**: 1日献立。
- 生成条件: 余り物食材 / 過去献立履歴 / 好み / 特売情報。
- 食事条件: **2人固定**、嗜好=バランス型、アレルギー=将来追加可能（スキーマに拡張余地）。
- 既存の「夕食=主菜/副菜/汁物の3品・昼食=1品」「直近重複NG・苦手NG」ルールは踏襲。
- フロー: AI提案 → 編集（カード/チャット）→ **確定で `meal_plans` 書込**（既存承認フロー踏襲）。

## 5. 買い物リスト

- **AI生成**（確定献立 + 余り物 + 特売から）。
- **共有対応**（世帯メンバー間で同一リストを参照）。
- **チェック機能必須**（購入済みのトグル状態を保持・永続化）。
- 既存の「最新N件保持・物理削除」は**履歴保存要件に合わせて見直し**（黙って消さない）。

❓未決: 買い物リストは「常時1つの共有リスト」か「献立ごとに生成される複数リスト」か。チェック状態のリアルタイム同期は必要か（Supabase Realtime）。

---

## 6. 特売情報

- 主対象: **マルエツ**（将来拡張可能な設計）。
- 取得: **Web自動取得**方針。ただし以下を**必須コンプライアンス前提**とする:
  1. 公式API/フィードの有無を優先確認。
  2. 利用規約・robots.txt の遵守、低頻度アクセス・キャッシュ。
  3. 個人利用スコープに限定。
  4. 取得不可/規約NG時は「チラシ画像のAI読取」または「手入力」へフォールバック。
- 用途: 献立生成・買い物リストの最適化入力。

❓未決: 取得頻度（日次? 週次?）と店舗指定（最寄り1店舗 vs 複数）。

## 7. タスク共有

- 単なるメモではなく**タスク管理**として設計。
- 例: 「牛乳を買う」「洗剤を買う」「病院予約」。
- **完了状態を持つ**（未完/完了、担当者、任意で期限）。
- 世帯メンバー間で共有。
- 買い物リスト（5章）とタスク（買い物系）の関係を整理（重複しうる）。

❓未決: タスクと買い物リストを統合するか分離するか。リマインド/通知は必要か。

## 8. AIチャット（アプリ全体に常駐）

- 全画面から呼べる常駐窓口（Life Assistant Agent）。
- 例: 「今月の支出は？」「来週の献立を考えて」「マルエツの特売を使った献立は？」。
- オーケストレーション: 意図解釈 → 適切なAgent（Finance/Recipe/Shopping/Planner）へ委譲 → 結果を提案として提示。
- **書込は常に承認フロー経由**。

❓未決: 「今月の支出は？」は account_records ベースの回答に読み替える（食費支出データが無いため）。表現の期待値をどう扱うか。

## 9. AI履歴

- 保存対象: 家計分析 / 献立提案 / レシピ生成 / 買い物提案。
- 世帯・ユーザー・種別・入力・出力・確定有無を記録。
- 既存の「最新1件のみ保持」設計を**履歴蓄積型**へ変更。
- 将来のベクトル検索（pgvector）に備えた拡張余地。

## 10. Agent構成（目標）

| Agent | 役割 | DB権限 |
|---|---|---|
| Life Assistant | 窓口・オーケストレーション | 書込不可（委譲のみ） |
| Finance | 家計・支出分析 | **読取のみ・提案のみ（書込禁止）** |
| Recipe | レシピ生成・URL/YouTube解析 | 提案 → 承認で書込 |
| Shopping | 特売分析・買い物リスト生成 | 提案 → 承認で書込 |
| Planner | 献立・食事計画 | 提案 → 承認で書込 |

- すべて Agent Server（**TypeScript/Node** + Claude Agent SDK）上で動作。
- AIキーはサーバ保管。クライアントからキーを排除。

## 11. 非機能要件

| 区分 | 要件 |
|---|---|
| セキュリティ | RLS厳格化、anon直アクセス廃止、AIキーのサーバ退避、Supabase Auth |
| 環境分離 | **Local / Development / Production** の3環境。本番は読取検証→承認→反映 |
| バックアップ | 本番のPITR/日次ダンプ確立（S0、実データ保護のため最優先） |
| テスト | 振込計算を純粋関数化しユニットテストで凍結（Flutter移植のリグレッション防止） |
| 型安全 | Supabase型自動生成を導入 |
| 監視 | 最低限のエラートラッキング（段階導入） |
| Docker | Local Supabase / Agent Server / （Flutter開発）をコンテナ化 |

## 12. Docker / 環境分離 構成（提案）

```
repo/
├─ apps/
│  ├─ web/            # 現React（移行期は維持）
│  ├─ mobile/         # Flutter（後期）
│  └─ agent-server/   # Node+TS, Claude Agent SDK  ← Dockerfile
├─ supabase/          # schema, migrations, seed（supabase CLIでLocal起動）
└─ docker-compose.yml # supabase(local) + agent-server (+ web dev)
```

- **Local**: `supabase start`（Docker）でPostgres/Auth/Storageをローカル再現 + agent-server をcompose起動。
- **Development**: 専用Supabaseプロジェクト。CIはここへ自動マイグレーション。
- **Production**: 手動承認デプロイのみ。マイグレーションは事前にDevで検証済みのものだけ。

## 13. Flutter移行戦略（後期・順序厳守）

現行解析 → 要件定義 → アーキ設計 → **Agent Server API契約の安定化** → Flutter移行戦略策定 → Flutter実装。
- **API契約が先、UIは後**。Webと並行運用し、機能単位で段階移行。
- 共有ロジック（計算式）はサーバ側API or Dartで再実装＋テストで担保。

## 14. 段階的移行計画（Phase4反映版）

| Stage | 目的 | 主作業 | 本番影響 |
|---|---|---|---|
| **S0** | 保護（最優先） | 本番バックアップ/PITR確認、現状schema固定 | 読取のみ |
| **S1** | 環境分離 | Supabase Local(Docker)+Dev構築、seed整備、Docker compose | なし |
| **S2** | ロジック保全 | 振込計算を純粋関数+テスト化（現挙動凍結） | なし |
| **S3** | Agent Server最小 | Node+TS BFF新設、AIキー退避、AI呼出をサーバへ移設 | なし（並行） |
| **S4** | 認証+RLS | Supabase Auth、households/members、RLS厳格化（一体実施） | 計画メンテ枠 |
| **S5** | 家計AI分析(MVP) | account_records推移分析（読取専用）をAgent化 | 追加のみ |
| **S6** | データモデル拡張 | AI履歴・タスク・買い物チェック状態テーブル追加 | 追加のみ |
| **S7** | レシピ/献立/特売/買い物 再設計 | URL/YouTubeサーバ解析、特売取得、買い物共有 | 追加のみ |
| **S8** | AIチャット常駐 + マルチAgent | Life Assistant + 各Agent統合 | 追加のみ |
| **S9** | Flutter移行 | API安定後にFlutter着手、Web並行維持 | なし |

各Stageは「Dev環境で回帰確認 → 承認 → 本番反映」。`account_records`への変更は追加のみ・後方互換。
